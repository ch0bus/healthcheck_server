Шпаргалка по типовым инцидентам
================================

## 1. Переполненный диск

### Симптомы

- Ошибки `No space left on device`.
- Сервисы падают или не могут записать логи.

### Диагностика

```bash
df -hT     # свободное место по файловым системам
df -ih     # inode (количество файлов)

# поиск крупных директорий в корне
.du -xhd1 / | sort -h

# поиск крупных директорий в /var
.du -xhd1 /var | sort -h
```

### Типовые места утечек

- Логи: `/var/log`, особенно большие `.log` и `.gz`.
- Временные файлы: `/tmp`, `/var/tmp`.
- Кэши приложений, бэкапы, дампы БД.

### Быстрые действия (с осторожностью)

```bash
# удалить старые ротации логов (пример)
sudo rm /var/log/*.gz

# очистить журналы journalctl (оставить 100M)
sudo journalctl --vacuum-size=100M
```

## 2. Упал/не стартует nginx

### Симптомы

- HTTP 502/504/5xx
- `systemctl status nginx` показывает failed

### Диагностика

```bash
systemctl status nginx
journalctl -u nginx -b --no-pager

sudo nginx -t   # проверка конфигурации
```

Частые причины:

- Ошибка в конфиге (опечатка, лишняя директива).
- Порт 80/443 уже занят другим процессом.

Проверка порта:

```bash
ss -tulpen | grep ':80'
ss -tulpen | grep ':443'
```

## 3. Проблемы с DNS

### Симптомы

- `ping 8.8.8.8` работает, а `ping google.com` — нет.
- Медленные ответы при обращении к доменам.

### Диагностика

```bash
ping -c 4 8.8.8.8
ping -c 4 google.com

# проверка DNS‑записей
dig google.com

# какой DNS-сервер используется
cat /etc/resolv.conf
```

Возможные решения:

- Временно прописать публичный DNS (1.1.1.1, 8.8.8.8) в `/etc/resolv.conf` или в настройках сети.
- Проверить, не упал ли локальный DNS‑резолвер (systemd‑resolved, bind, unbound и т.п.).

## 4. Высокая нагрузка CPU/памяти

### Диагностика

```bash
uptime
htop

ps aux --sort=-%cpu | head -15
ps aux --sort=-%mem | head -15
```

Дальше действуем по алгоритму из `seek_and_destroy.txt`:

1. Найти тяжёлый процесс.
2. Определить, какому пакету он принадлежит (`which`, `dpkg -S`).
3. Проверить, насколько критичен этот пакет.
4. При необходимости — ограничить, перезапустить сервис или удалить пакет.

## 5. Сервис не стартует после ребута

### Диагностика

```bash
systemctl status ИМЯ_СЕРВИСА
journalctl -u ИМЯ_СЕРВИСА -b
systemctl is-enabled ИМЯ_СЕРВИСА
```

Проверяем:

- Включён ли автозапуск (`enabled`).
- Нет ли ошибок в конфиге.
- Все ли зависимости доступны (сеть, диски, каталоги).

---

## 6. Минимальный чек‑лист при инциденте

1. **Понять симптом**: что именно не работает (HTTP, SSH, база, диск и т.п.).
2. **Собрать состояние**:
   - `uptime`, `free -h`, `df -hT`
   - `systemctl --failed`
   - `ss -tulpen`
3. **Посмотреть логи** нужного сервиса через `journalctl` и/или в `/var/log`.
4. **Сделать минимальное безопасное действие** (перезапуск сервиса, очистка кэша, ротация логов).
5. **Зафиксировать** команды и результат (для последующего анализа и доработки шпаргалок).
